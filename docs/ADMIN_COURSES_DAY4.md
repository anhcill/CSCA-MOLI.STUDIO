# CSCA Admin Courses — Day 4

Day 4 adds the backend CMS boundary for CSCA courses. `index.js` mounts it at `/api/admin/courses` only when `CSCA_COURSES_ENABLED=true`; the flag remains off by default until migrations 052–054 are applied.

## Authorization

Every endpoint requires both `authenticate` and `authorizePermission("content.manage")`.

| Method | Path | Purpose |
|---|---|---|
| `GET` | `/api/admin/courses` | List and filter courses (`q`, `subjectCode`, `status`, `page`, `limit`) |
| `GET` | `/api/admin/courses/:courseId` | Course with full draft curriculum |
| `POST` | `/api/admin/courses` | Create a draft/review/archived course |
| `PATCH` | `/api/admin/courses/:courseId` | Update explicitly allowed course fields |
| `POST` | `/api/admin/courses/:courseId/sections` | Create section |
| `PATCH` | `/api/admin/courses/:courseId/sections/:sectionId` | Update an owned section |
| `POST` | `/api/admin/courses/:courseId/lessons` | Create lesson |
| `PATCH` | `/api/admin/courses/:courseId/lessons/:lessonId` | Update an owned lesson and attach video |
| `POST` | `/api/admin/courses/:courseId/publish` | Validate readiness and publish |
| `POST` | `/api/admin/courses/:courseId/unpublish` | Return to draft |
| `POST` | `/api/admin/courses/:courseId/archive` | Archive |

Responses use the standard `{ success, data }` course envelope. DTO fields are camelCase and all IDs are JSON numbers.

## Invariants

- Subjects are limited to `MATH`, `PHYSICS`, `CHEMISTRY`, `CHINESE_SCI`, and `CHINESE_SOC`.
- Levels are `basic`, `intermediate`, or `advanced`; access is `free`, `vip`, `premium`, `contact`, or `private`.
- `externalKey` is generated by the server for courses and lessons. Client values are never persisted.
- `requiredTier` is derived from access: `vip → vip`, `premium → premium`, otherwise `basic`.
- Publishing cannot be performed through generic `PATCH`; the publish endpoint must be used.
- HTML in `descriptionHtml` and lesson `contentHtml` is allow-list sanitized with `sanitize-html`.
- Repository updates use fixed field-to-column maps. Unknown JSON properties are ignored and cannot become SQL assignments.
- Section and lesson IDs are checked together with `courseId`; cross-course curriculum mutation returns a stable not-found/validation error.
- Every section/lesson mutation and aggregate refresh runs in one database transaction.
- A curriculum edit cannot leave an already-published course in a non-publishable state; unpublish first when making such a change.

## Video attachment and publishing

The intended flow is:

1. Create the lesson without `videoAssetId`.
2. Use the existing media upload flow with that `courseId` and `lessonId`.
3. The admin UI may immediately `PATCH` the lesson with the new `videoAssetId` while the asset is still `processing`; publishing remains blocked until processing marks the asset and at least one HLS variant `ready`.

Attachment atomically claims only an undeleted `purpose=lesson` asset whose `course_id` matches and whose `lesson_id` is either empty or already the target lesson. Cross-course and cross-lesson assets are rejected.

A course may publish only when it has at least one published section and one published lesson. Every published video lesson must point to an undeleted asset that:

- belongs to the same course and lesson;
- has status `ready`;
- has a non-empty HLS master object key; and
- has at least one ready HLS variant.

The generic course schema has no `created_by`/`updated_by` fields, so Day 4 does not fabricate audit columns or add a migration. Video creation continues to use the existing `created_by` support. A later audit-log migration may record CMS actors centrally.

## Stable error codes

Important codes include `ADMIN_COURSE_NOT_FOUND`, `ADMIN_COURSE_SECTION_NOT_FOUND`, `ADMIN_COURSE_LESSON_NOT_FOUND`, `ADMIN_COURSE_SLUG_CONFLICT`, `ADMIN_COURSE_EXTERNAL_KEY_CONFLICT`, `ADMIN_COURSE_VIDEO_ASSET_INVALID`, `ADMIN_COURSE_NOT_READY_TO_PUBLISH`, and `ADMIN_COURSE_VALIDATION_FAILED`.

No build, server, database, migration, upload, or deployment command is part of Day 4 verification. Static verification uses `node --check` and pure validation mocks only.
